Spec: RuneMetrics Scraper — Adaptive Throttling on Excessive Failures

New Component Modified Base Modified Base (hiscore_scraper) Tests

Problem Statement

The runemetrics_scraper worker consumes players from the players.not_found Kafka topic and fetches their RuneMetrics profiles via the RuneScape API. When the upstream RuneScape service is degraded or offline, it returns 302 redirects to the main page instead of profile data. The scraper detects this as UnexpectedRedirection and requeues the player with a flat sleep(10).

This flat sleep causes two problems:

  1. Hammering a down service: All workers wake up every 10 seconds and immediately hit the same failing endpoint, generating useless traffic and wasting proxy quota.
  2. No observability: There are no Prometheus metrics for retry counts or backoff delays, making it impossible to detect or alert on sustained outages.

The sibling hiscore_scraper already solves this problem with an RetryTracker that provides adaptive exponential backoff with jitter and time decay. This spec proposes extracting that tracker into a shared component and applying it to the runemetrics_scraper.

Solution

Extract the existing RetryTracker from the hiscore_scraper base into a new shared Polylith component (retry_tracker). Integrate it into the runemetrics_scraper base so that every scrape error triggers per-worker exponential backoff with jitter and time decay, replacing the current flat 10-second sleep. Add Prometheus metrics for retry count, consecutive failures, and backoff delay. Refactor the hiscore_scraper to import from the new shared component.

User Stories

  1. As a system operator, I want the runemetrics_scraper to back off exponentially when the RuneScape API is returning errors, so that I don't waste proxy quota on futile requests.
  2. As a system operator, I want backoff to apply jitter, so that all workers don't wake up simultaneously and cause a thundering-herd spike.
  3. As a system operator, I want the backoff delay to decay after a quiet period, so that the scraper recovers quickly once the upstream service returns to health.
  4. As a system operator, I want a successful scrape to reset the backoff counter, so that the scraper returns to full speed immediately after recovery.
  5. As a system operator, I want a hard cap on the maximum backoff delay (e.g. 300 seconds), so that a worker never stalls indefinitely.
  6. As a system operator, I want Prometheus metrics for retry attempts, consecutive failure counts, and applied backoff delays, so that I can monitor and alert on sustained outages.
  7. As a system operator, I want the throttling to apply to all transient scrape errors (UnexpectedRedirection, ClientResponseError, ConnectionTimeoutError, ClientConnectorError, ServerDisconnectedError), so that any persistent failure mode is handled gracefully.
  8. As a developer, I want the RetryTracker extracted into a shared Polylith component, so that both the hiscore_scraper and runemetrics_scraper can reuse it without code duplication.
  9. As a developer, I want the RetryTracker to remain configurable (base_delay, max_delay, decay_window, jitter_factor), so that each scraper can tune parameters independently.
  10. As a developer, I want the hiscore_scraper's existing behavior to remain unchanged after the refactor, so that this change introduces no regression.
  11. As a developer, I want the RetryTracker interface to be fully typed, so that mypy can catch integration errors at development time.
  12. As a developer, I want the RetryTracker to use the error-as-value pattern (no exceptions thrown), so that it aligns with the codebase conventions in AGENTS.md.
  13. As a system operator, I want the runemetrics_scraper to still requeue players on error (with commit), so that no players are lost during outages.
  14. As a system operator, I want the RetryTracker parameters to be configurable via environment variables (with sensible defaults), so that I can tune throttling without redeploying.
  15. As a developer, I want the RetryTracker to have comprehensive unit tests, so that I can trust the backoff calculation logic is correct.
  16. As a developer, I want the runemetrics_scraper work loop tests updated to verify backoff behavior, so that the integration is verified.

Implementation Decisions

1. New Component: retry_tracker

A new Polylith component will be created at components/bot_detector/retry_tracker/.

  • Interface: Exports RetryTracker and RetryState.
  • RetryTracker is a class (not a module of functions) because it holds per-worker mutable state in a dict[int, RetryState].
  • RetryState is a dataclass with fields: consecutive_failures: int, last_attempt: float, last_success: float | None.
  • Constructor parameters: base_delay: float = 10.0, max_delay: float = 300.0, decay_window: float = 300.0, jitter_factor: float = 0.5.
  • Methods:
    • get_backoff_delay(worker_id: int) -> float — returns the delay in seconds after applying exponential backoff, cap, and jitter.
    • record_attempt(worker_id: int, success: bool = False) — records a success (resets) or failure (increments).
    • get_retry_count(worker_id: int) -> int — returns consecutive failure count (with decay applied).
  • Backoff formula: delay = min(base_delay * 2^consecutive_failures, max_delay), then delay * uniform(1 - jitter_factor, 1 + jitter_factor), clamped to [1.0, max_delay].
  • Time decay: If now - last_attempt > decay_window, consecutive_failures resets to 0 before computing delay.
  • No exceptions thrown. All methods return values. This aligns with the AGENTS.md error-as-value convention.
Rationale: Extracting into a component follows Polylith rules. Both scrapers (bases) can depend on the component. No circular dependencies introduced. The component has no framework or infrastructure concerns — pure business logic.

3. Modify runemetrics_scraper Base

The base at bases/bot_detector/runemetrics_scraper/ will be modified:

  • Add import: from bot_detector.retry_tracker import RetryTracker
  • Instantiate per worker: A RetryTracker instance will be created inside work() (local to each worker coroutine, matching the hiscore_scraper pattern). Suggested defaults: base_delay=10.0, max_delay=300.0, decay_window=300.0.
  • On scrape error: After requeuing the player, call retry_tracker.record_attempt(worker_id, success=False), compute delay via retry_tracker.get_backoff_delay(worker_id), and await asyncio.sleep(delay) instead of the current flat sleep(10).
  • On scrape success: Call retry_tracker.record_attempt(worker_id, success=True) to reset the backoff counter.
  • Replace flat sleep: The two remaining await asyncio.sleep(10) calls (no proxy available, no player available) remain unchanged — they are not scrape errors and don't affect backoff state.
  • ValidationError path: The ValidationError handler during ScrapedStruct construction also requeues the player but currently has no sleep. This spec does not add throttling here since validation errors indicate a data issue, not a transient upstream failure.

4. Add Prometheus Metrics to runemetrics_scraper

5. Refactor hiscore_scraper Base

  • Remove: The file bases/bot_detector/hiscore_scraper/retry_tracker.py will be deleted.
  • Add import: from bot_detector.retry_tracker import RetryTracker replaces the relative import from .retry_tracker import RetryTracker.
  • No behavioral change. The RetryTracker API is identical. All existing hiscore_scraper tests must pass without modification.

7. Error Categories in scrape_player

The scrape_player function currently catches specific exceptions and returns a string error. This does not change. All error paths (UnexpectedRedirection, ClientResponseError, ConnectionTimeoutError, ClientConnectorError, ServerDisconnectedError) will trigger the backoff in the work() loop when error is not None.

8. Interaction Flow (After Change)

The work() loop changes from:

Before: On error → requeue → sleep(10) → continue
After: On error → requeue → retry_tracker.record_attempt(worker_id, success=False) → compute backoff delay → observe Prometheus metrics → sleep(delay) → continue

On success → retry_tracker.record_attempt(worker_id, success=True) → continue

Testing Decisions

General Testing Philosophy

  • Test external behavior (inputs and outputs), not implementation details.
  • Use standalone @pytest.mark.asyncio functions; no test classes.
  • Use explicit mocks and fixtures.
  • Each test validates a single concern.

Module: retry_tracker component (new tests)

New test file: test/components/bot_detector/retry_tracker/test_core.py

  • Test initial backoff delay: A fresh tracker returns a delay near base_delay for a worker with no prior attempts.
  • Test exponential growth: After N failures, the delay is approximately base_delay * 2^N (within jitter range).
  • Test max delay cap: After many failures, the delay never exceeds max_delay.
  • Test jitter range: The returned delay is within [delay * (1 - jitter_factor), delay * (1 + jitter_factor)].
  • Test success resets counter: After failures, a success record resets the delay to near base_delay.
  • Test time decay: If decay_window seconds pass without an attempt, the failure count resets to 0 and delay returns to base_delay.
  • Test per-worker isolation: Failures for worker 0 do not affect the delay for worker 1.
  • Test get_retry_count with decay: Returns 0 when decay window has passed since last attempt.
  • Test minimum delay clamp: Returned delay is never below 1.0 second.

Module: runemetrics_scraper base (updated tests)

Existing test file: test/bases/bot_detector/runemetrics_scraper/test_core.py

  • Update test_work_commits_offset_after_successful_handle: Verify that retry_tracker.record_attempt(worker_id, success=True) is called on successful scrape.
  • Update test_work_commits_only_after_successful_requeue: Verify that retry_tracker.record_attempt(worker_id, success=False) is called on scrape error.
  • New test: test_work_uses_exponential_backoff_on_error: Mock the sleep function; verify the sleep duration increases with successive errors for the same worker.
  • New test: test_work_resets_backoff_on_success: After errors followed by a success, verify the next error sleep returns to base delay.
  • New test: test_work_records_retry_metrics_on_error: Verify Prometheus retry counters are incremented on scrape error.

Module: hiscore_scraper base (regression tests)

  • Run existing tests unchanged: All existing hiscore_scraper tests must pass after swapping the import from the shared component. This is the regression check.

Prior Art

  • test/bases/bot_detector/runemetrics_scraper/test_core.py — pattern for mocking work() dependencies with monkeypatch.
  • test/components/bot_detector/osrs_hs_api/test_core.py — pattern for HTTP mocking with aioresponses.

Out of Scope

  • Circuit breaker / global pause: This spec only addresses per-worker exponential backoff. A global circuit breaker that halts all workers simultaneously is a future enhancement.
  • Refactoring runemetrics_api to use Result types: The runemetrics_api component currently raises exceptions (UnexpectedRedirection, etc.) rather than returning Ok/Err result types. This is inconsistent with AGENTS.md guidance but is out of scope for this spec.
  • Configurable retry_tracker parameters via environment variables: While desirable (user story #14), the initial implementation will use hardcoded defaults matching the hiscore_scraper. Environment-based configuration can be added in a follow-up.
  • Handling uncaught exceptions in work(): The current work() loop only catches specific aiohttp exceptions. A broad except Exception at the base boundary would prevent worker crashes, but this is a separate concern.
  • Adding throttling to the ValidationError path in work(): Validation errors indicate data corruption, not transient failures.
  • Refactoring Prometheus metrics into a separate module: The runemetrics_scraper currently defines metrics inline in core.py. Moving them to a metrics.py module (like hiscore_scraper does) is a cleanup step that can be bundled with this change but is not a core requirement.

Further Notes

  • Polylith permission: This spec requires creating a new component (retry_tracker). Per AGENTS.md agent guardrails, this requires explicit approval. The justification is: the component is pure business logic with no framework or infrastructure concerns, and it is shared by two bases.
  • Polylith command: The component should be created using uv run poly create component --name retry_tracker to follow the standard workspace scaffolding.
  • Default parameter alignment: The suggested defaults (base_delay=10.0, max_delay=300.0, decay_window=300.0) match the current flat sleep of 10 seconds as the baseline, with a 5-minute maximum delay. This is intentionally more conservative than the hiscore_scraper's base_delay=1.0.
  • Thread safety: The RetryTracker is used from asyncio coroutines within a single event loop. Since asyncio is single-threaded and each worker has a unique worker_id, no locking is needed.
  • Kafka requeue semantics: Players are always requeued on error (as they are today). The backoff only affects when the worker picks up the next player, not whether the failed player is preserved.
  • Deployment impact: Both the runemetrics_scraper and hiscore_scraper projects must be rebuilt and redeployed. The hiscore_scraper change is a pure refactor with no behavioral change, but it should still be deployed to ensure the dependency on the new component is resolved at runtime.
